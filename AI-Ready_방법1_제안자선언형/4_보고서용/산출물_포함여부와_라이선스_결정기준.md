# 스키마와 참조구현 — 표준 문서 포함 여부와 라이선스 결정 기준

작성일: 2026-08-18 · 근거: [3_근거_국제선례](../3_근거_국제선례/)

**두 질문은 얽혀 있다.** 문서에 포함되는지가 어느 라이선스를 적용할지를 좌우하기 때문이다.

- 부속서에 수록되면 → 표준 문서의 저작권 규정이 미치는 범위 안에 들어온다
- 파일로 나가면 → 그 파일에 별도 표시가 필요하다

---

## 1. 스키마 — 포함 여부

### 1-1. 세 가지 선택지 중 하나는 배제해야 한다

| | 방식 | 규범성 | 기계 접근성 | 국제 사례 |
|---|---|---|---|---|
| (a) | 부속서 수록**만** | 확보 | **불가** — 문서에서 추출해야 함 | **0건** |
| (b) | **부속서 수록 + 파일 병행 제공** | 확보 | 가능 | LoC PREMIS·MODS·METS, DDI, OGC, ISO |
| (c) | 규범적 참조 + 외부 파일 | 확보 | 가능 | ECMA-424 |

**(a)는 채택하지 않는다.** 기계가 읽으라고 만든 산출물을 사람용 문서 안에만 두면 목적에 어긋난다. 국제 사례 16건 중 **표준 문서 파일 안에 스키마를 담은 사례는 0건**이고, 모두 문서 밖에 파일로 제공한다.

그렇다고 부속서를 빼면 규범성이 사라진다(작성지침 6.6 "본 부속서는 표준 내용의 일부임"). **둘 다 하는 (b)가 답이다.**

### 1-2. 병행형과 참조형을 가르는 기준

**병행형이 원칙, 참조형이 예외**다. 예외 사유는 세 가지로 한정한다(운영요령 제19조의3제3항).

| 사유 | 판단 | 실례 |
|---|---|---|
| **① 분량** | 문서에 수록하기 곤란한가 | HL7 FHIR은 XSD 323개, ISO 19115-3은 117개 |
| **② 개정 주기** | 표준 문서와 다른 주기로 바뀌는가 | 스키마를 고칠 때마다 표준 개정 절차를 밟을 수는 없다 |
| **③ 모듈 의존** | 다른 파일을 인용·포함하여 단일 파일로 완결되지 않는가 | OGC `gml.xsd`는 모듈 28개를 include하는 진입점일 뿐이다 |

**②가 실무상 가장 자주 걸린다.** 분량이 작아도 스키마가 문서보다 자주 바뀌면 부속서에 넣는 순간 개정 부담이 생긴다.

### 1-3. 산출물마다 따로 정한다

한 표준이 여러 산출물을 낼 때 **형태를 통일할 필요가 없다.**

| 산출물 | 통상 | 이유 |
|---|---|---|
| JSON-LD @context | **병행형** | 요소↔IRI 매핑표라 분량이 작고 문서와 함께 개정된다 |
| 검증용 JSON Schema·XSD | 상황에 따라 | 단일 파일이면 병행형, 모듈이 여럿이면 참조형 |
| RDF 어휘(Turtle) | 상황에 따라 | 네임스페이스 역참조를 쓰면 참조형이 자연스럽다 |

## 2. 스키마 — 라이선스

### 2-1. 부속서에 수록해도 별도 표시가 필요하다

**표준 문서의 저작권 문구가 산출물에 자동으로 미친다고 볼 수 없다.**

선례가 있다. IETF Trust Legal Provisions 5.0 제4조는 문서 **안**의 코드에 `<CODE BEGINS>` 표시를 붙여 구분하고, 문서와 **다른 라이선스**(Revised BSD)를 적용하며 이렇게 못 박는다.

> "the additional licenses and restrictions set forth in Section 3 **shall not apply thereto**"
> — 제3조에 정한 추가 허락과 제한은 **그 코드에 적용되지 아니한다**

그래서 운영요령 제19조의3제7항에 "**부속서에 수록한 경우에도 같다**"를 넣었다.

### 2-2. 어느 라이선스인가

| 후보 | 판단 | 근거 |
|---|---|---|
| **CC BY 4.0** | **권고** | 표준 문서와 일관 · 데이터베이스권 포함 · SA 없음 |
| CC BY-SA 3.0/4.0 | 피한다 | 동일조건변경허락이 **파생 어휘에 전염**된다. Schema.org가 이 조건이라 정의문 전재 시 주의가 필요하다 |
| Apache-2.0 | 차선 | 특허 조항은 강점이나 NOTICE·변경고지 의무가 문서 배포 관행과 맞지 않는다 |
| CC0 1.0 | 가능 | 최대 확산이 목표라면. 다만 한국법상 저작권 포기가 제한되어 제3조 폴백에 기대야 한다 |
| **표기 없음** | **금지** | ISO 19115-3이 XSD 117개를 무료 공개하고도 파일에 아무 표시가 없어 재배포 가능 여부를 알 수 없다 |

**특허 공백은 라이선스가 아니라 IPR 정책으로 메운다.** CC 계열은 특허를 다루지 않지만(CC BY 4.0 제2조(b) "Patent and trademark rights are not licensed under this Public License"), TTA에는 운영규정 제36조와 IPR요령의 확약 체계가 이미 있다. 운영요령 제19조의3제10항이 산출물을 표준초안의 일부로 보아 제19조제1항제1호의 확인 대상에 포함시킨다.

### 2-3. 어떻게 표시하는가

형식마다 방법이 다르다(작성지침 6.6).

| 형식 | 방법 | 실례 |
|---|---|---|
| XSD · Turtle · Protobuf | 주석으로 파일 머리말에 기재 | CycloneDX `bom-1.7.xsd` |
| **JSON Schema** | 주석을 쓸 수 없으므로 최상위 `$comment` 키 | CycloneDX `bom-1.7.schema.json` |
| RDF 어휘 | `dcterms:license` 트리플 — **기계가 읽을 수 있다** | W3C `dcat.ttl` |

## 3. 참조구현 — 다르게 결정한다

### 3-1. 포함 여부는 판단할 것이 없다

**항상 표준 밖이다.** 부록에 위치만 안내한다(운영요령 제19조의3제8항).

| 이유 | 설명 |
|---|---|
| 노후화 | 언어·런타임·의존성에 묶여 있어 표준으로 고정하면 곧 낡는다 |
| 지식재산권 범위 | 실행 가능한 코드에 표준 지위를 주면 확인·확약 범위가 통제 불가능하게 넓어진다 |

### 3-2. 라이선스는 스키마와 같을 필요가 없다

**Schema.org가 정확히 그렇게 한다** — 어휘는 CC BY-SA 3.0, 빌드 도구는 Apache-2.0. W3C도 문서용과 소프트웨어용 라이선스를 나눠 둔다.

참조구현은 **실행 가능한 코드**라 특허 위험이 실재한다. CC 계열은 특허를 다루지 않으므로 부적합하고, **특허 조항이 있는 소프트웨어 라이선스**(Apache-2.0 등)가 맞다.

**다만 규정은 종류를 강제하지 않는다.** 표준 밖 자산이므로 제안자가 정하되, 위치와 함께 이용조건을 밝히게 한다. 협회는 내용을 보증하지 않는다.

## 4. 한 장 정리

| | 문서 포함 | 라이선스 | 표시 위치 |
|---|---|---|---|
| **스키마** | **병행형**(부속서 수록 + 파일 제공)이 원칙<br>분량·개정주기·모듈의존 사유가 있으면 참조형 | **CC BY 4.0** 권고<br>SA·무표기 금지 | **파일 자체**에 필수<br>(부속서 수록분도 별도 표시) |
| **참조구현** | **항상 밖.** 부록에 위치만 안내 | 제안자 자율<br>특허 조항 있는 코드 라이선스 권고 | 코드 저장소 |

### 결정 순서

```
1. 이 산출물이 규범인가?
   예 → 2로.   아니오 → 참조구현으로 취급(부록 안내)

2. 부속서에 수록할 수 있는가?
   · 분량이 문서에 들어가는가
   · 표준 문서와 같은 주기로 개정되는가
   · 단일 파일로 완결되는가
   셋 다 예 → 병행형.   하나라도 아니오 → 참조형

3. 라이선스를 정한다 (형태와 무관하게 필요)
   기본 CC BY 4.0 · SA 조건은 피함 · 무표기 금지

4. 형식에 맞는 방법으로 파일에 표시한다
   XSD·TTL → 주석 / JSON Schema → $comment / RDF → dcterms:license
```
