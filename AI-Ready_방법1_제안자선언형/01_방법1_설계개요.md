# 방법1 — 제안자 선언형 AI-Ready 표준화 (설계 개요)

작성일: 2026-08-15
기준 규범: 운영규정 SAG-0029(24)/R24(2025.6.27.) · 운영요령 SBG-0030(13)/R13(2025.6.13.) · 작성지침 TTAR-09.0040/R1(2025.5.23.)

> 이 문서군은 **방법2(공동 에디터 보강형)와 별개의 독립 개정안**이다. 현행 규범을 기준으로 작성했으며, 방법2 문서를 참조하거나 전제하지 않는다.

---

## 1. 핵심 구조

**표준 제안자가 어휘를 선언하고 스키마까지 제공한다. 협회는 별도의 어휘 전문가를 배정하지 않는다.**

```
제안자
  ├─ ① 어휘 선언 ────── 사용하는 전역 어휘와 그 식별자(IRI)를 밝힌다
  ├─ ② 스키마 제공 ──── 기계가독 산출물(JSON Schema·XSD·RDF 어휘 등)을 작성해 제출한다
  ├─ ③ 외부 공개 (선택) ─ GitHub 등 저장소에 공개할 수 있다
  └─ ④ 참조구현 (선택) ─ 스키마를 이용하는 프로그램 코드를 공개할 수 있다

협회
  ├─ 채택 시점 사본을 보관하고 표준과 함께 공개한다
  └─ 형식 정합성을 전자적 방법으로 점검할 수 있다
```

## 2. 세 가지 설계 판단

### 2-1. 스키마는 규범이다

제안자가 제공하는 기계가독 산출물은 **표준의 규범 내용**이다. 이를 따르지 않으면 그 표준에 적합하다고 할 수 없다. 참고 자료가 아니다.

이 판단에서 아래 요건이 따라 나온다.

| 요건 | 이유 |
|---|---|
| 부속서에 수록하거나 규범적으로 참조 | 규범이므로 표준의 구성요소여야 한다 |
| 지식재산권 확인 대상 포함 | 표준의 일부이므로 운영규정 제36조 적용 |
| 협회 보관본 유지 | 외부 저장소가 사라져도 규범이 남아야 한다 |
| 이용조건(라이선스) 명시 의무 | 규범을 이용자가 쓸 수 있어야 실효가 있다 |

### 2-2. 외부 공개를 허용하되, 보관본을 정본으로 둔다

제안자가 GitHub 등에 스키마를 공개하는 것을 허용한다. 개발자 접근성과 이슈 추적·버전 관리 이점이 크기 때문이다.

다만 외부 저장소는 제안자가 삭제·변경할 수 있으므로 표준의 영속성과 충돌한다. 그래서 **협회가 채택 시점의 사본을 보관하고, 외부 공개본과 다를 경우 보관본을 따른다.**

이 이중 구조는 CycloneDX가 실제로 쓰는 방식과 같다. 스키마는 GitHub에서 배포하되 같은 버전을 Ecma가 ECMA-424 정식 판으로 승인해 공식성과 영속성을 확보한다.

### 2-3. 참조구현 코드는 표준이 아니다

스키마를 이용하는 프로그램 코드는 **표준의 일부가 아니다.** 위치를 부록에 안내할 수 있을 뿐이며, 협회는 그 내용을 보증하지 않는다.

구분하는 이유는 두 가지다. 첫째, 코드는 언어·런타임·의존성에 묶여 있어 표준으로 고정하면 곧 낡는다. 둘째, 코드에 표준의 지위를 주면 지식재산권 처리 범위가 통제 불가능하게 넓어진다.

## 3. 현행 규범 안에서 성립하는 근거

**운영규정을 개정하지 않는다.** 근거 조문이 이미 있다.

| 현행 조문 | 방법1에서의 역할 |
|---|---|
| 운영규정 제57조 | 운영위원회가 필요한 사항을 요령으로 정할 수 있음 → 방법1의 절차는 운영요령에 담는다 |
| 운영규정 제38조제2항·제3항 | 에디터 지정과 초안 작성 방법의 작성지침 위임 |
| 운영규정 제2조제3항 | 표준은 "본문, 부속서, 부록, 도표"로 구성 → 부속서는 표준의 일부 |
| 운영규정 제36조 | 표준에 지식재산권이 포함된 경우 처리 → 부속서에 담긴 규범은 자동 포섭 |
| 작성지침 6.6 | 부속서 번호 밑에 "(본 부속서는 표준 내용의 일부임)" 표기 |

**핵심 논리**: 기계가독 산출물을 부속서에 수록하거나, 부속서에 규범적 참조 명세를 두면 그것은 "표준 내용의 일부"가 된다. 따라서 지식재산권 취급·표준 관리·폐지 절차가 별도 조항 없이 그대로 적용된다.

외부 문서에 규범적으로 의존하는 것 자체는 새로운 개념이 아니다. **인용 표준(normative reference)이 이미 같은 구조**다. 방법1이 추가하는 것은 그 대상이 제안자의 저장소일 때 필요한 영속성 보완장치뿐이다.

## 4. 개정이 필요한 문서

| 규범 | 개정 여부 | 권한 |
|---|---|---|
| 정보통신표준화 운영규정 | **개정 불필요** — 기존 조문을 근거로 활용 | (표준총회) |
| 정보통신표준화 운영요령 | **신설·보강** | 운영위원회 (제57조) |
| 정보통신단체표준 작성지침 | **신설·보강** | 전략계획위원회·TC (제47조①) |

상정 순서는 **운영요령 → 작성지침**이다. 작성지침이 운영요령 조문을 참조하므로 운영요령이 먼저 의결되어야 한다.

## 5. 방법1이 감수하는 것

정직하게 적어 둔다.

**어휘 매핑 품질이 제안자 역량에 좌우된다.** 협회가 어휘 전문가를 붙이지 않으므로, 잘못된 IRI 매핑이나 부적절한 어휘 선택을 걸러낼 사람이 없다. 이를 보완하는 장치는 두 가지뿐이다 — 제안자 자가점검표와 사무국의 형식 정합성 자동 점검. 둘 다 **형식**은 잡아내지만 **의미**는 잡아내지 못한다.

**대신 얻는 것**은 확장성이다. 어휘 전문가 풀에 의존하지 않으므로 적용 대상 표준 수에 제약이 없고, 제안자가 이미 스키마를 갖고 있는 경우(산업계 제안, 오픈소스 기반 제안) 절차가 짧다.
