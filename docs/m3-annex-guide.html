별표 10 구성요소 해설

일곱 구성요소의 등급 판정과 예시. 「정보통신표준화 운영요령」 별표 10(안) 제1부의 일곱 구성요소를 하나씩 풀어 쓴 참고 자료다. 별표 10은 규범 문안이고, 이 문서는 그것을 적용하는 사람 — 제안자, 에디터, 기술위원회등 의장 — 이 등급을 판정할 때 곁에 두고 보는 해설이다. **규범이 아니며, 별표 10과 다르게 읽히는 곳이 있으면 별표 10에 따른다.**

① 시맨틱 — 요소의 뜻을 전역 어휘(IRI)에 연결했나

무엇을 묻는가

표준이 정의한 요소 "Title", "Creator", "수온"이 무슨 뜻인지를 기계가 다른 표준과 같은 뜻으로 알아볼 수 있는가다. 사람은 "제목"과 "Title"과 "dct:title"이 같은 것임을 알지만, 기계는 세 문자열을 서로 다른 것으로 본다. 요소를 국제적으로 합의된 어휘의 전역 식별자(IRI)에 연결하면, 이름이 달라도 같은 IRI를 가리키는 요소끼리 기계가 묶을 수 있다.

등급별 모습

  • 0 — 산문·자체 코드로만 설명. 요소 정의표에 "Title: 데이터의 제목"이라고만 적는다. 자체 코드표(예: 분류 코드 01=논문, 02=보고서)를 쓰되 그 코드가 무엇에 대응하는지 밝히지 않는다.
  • 1 — 일부 개념만 전역 어휘에 연결. 제목·작성자처럼 흔한 요소에만 "Dublin Core의 title에 해당"이라고 적고, 표준 고유의 요소나 코드값은 연결하지 않는다. 또는 연결은 했지만 IRI가 아니라 이름("DC.title")으로만 적었다.
  • 2 — 뜻과 관계까지 전역 IRI에 바인딩. 모든 요소에 IRI를 적고(대응 용어가 없으면 "자체 정의"로 명시), 코드값은 SKOS 개념으로, 요소 사이의 상하·포함 관계(예: 파일은 데이터세트의 일부)도 IRI로 적는다.

예시 — 요소 정의표의 IRI 컬럼

작성지침 6.5.7의 요소 정의표 마지막 컬럼이 이 구성요소의 실체다. TTAK.KO-10.0976의 일부를 요소 정의표로 옮기면 이렇다.

요소 이름 정의 데이터 유형 전역 어휘 식별자(IRI)
Title 데이터의 제목 문자열 http://purl.org/dc/terms/title
Creator 데이터를 만든 사람·기관 식별자 http://purl.org/dc/terms/creator
PublicationYear 공개 연도 연도 http://purl.org/dc/terms/issued
Dataset 데이터 묶음 클래스 http://www.w3.org/ns/dcat#Dataset
File 데이터세트를 이루는 파일 클래스 http://www.w3.org/ns/dcat#Distribution
isPartOf 상위 데이터세트 관계 http://purl.org/dc/terms/isPartOf
SubjectScheme 주제 분류 체계 식별자 http://www.w3.org/2004/02/skos/core#inScheme

"File"과 "isPartOf"가 2등급의 차이를 보여 준다. 파일이라는 개념(dcat:Distribution)뿐 아니라 "파일은 데이터세트의 일부"라는 관계까지 IRI로 잡았다.

어느 기술 대상 프로파일이 요구하나

모든 기술 대상 프로파일의 필수다. ① 지식정보, ② 자기기술형 레코드, ② 중 참조표준·물성, ③ AI 데이터세트, ④ 품질 지표 어디서든 ①②(= L1)가 기준선이다.

흔한 함정

  • "참조함"과 "매핑함"의 혼동. 표준 서문에 "본 표준은 Dublin Core를 참조하였다"고 쓰는 것은 0등급이다. 요소마다 어느 IRI인지 적어야 1 이상이다.
  • IRI를 가리키는 것과 정의문을 옮겨 적는 것의 혼동. IRI를 적는 것은 저작권 확인 대상이 아니고 직접 인용에도 해당하지 않는다(작성지침 6.5.3 단서). 반대로 그 어휘의 정의문을 요소 정의표에 그대로 옮겨 적으면 전재가 된다.
  • 억지 매핑. 뜻이 조금 다른 기존 용어에 끼워 맞추는 것보다 "자체 정의"로 밝히는 편이 낫다. 잘못된 매핑은 기계가 서로 다른 것을 같은 것으로 묶게 만든다.

② 신태틱 — 그 매핑을 기계가 읽는 형식으로 냈나

무엇을 묻는가

①에서 만든 요소↔IRI 매핑을 기계가 파일로 읽어 들일 수 있는 형식으로 냈는가다. 요소 정의표의 IRI 컬럼은 사람이 읽는 표다. 같은 내용을 JSON-LD나 RDF 같은 직렬화 형식으로 내야, 표준을 따른 데이터 파일을 기계가 받아 곧바로 전역 어휘로 해석할 수 있다.

등급별 모습

  • 0 — 직렬화 규범 없음. 데이터를 어떤 형식으로 주고받는지 정하지 않거나, 정하더라도 요소 이름만 쓰는 XML·JSON이어서 IRI 매핑이 형식에 실리지 않는다.
  • 1 — 형식 언급은 있으나 비규범. "JSON-LD로 표현할 수 있다", "참고로 RDF 예시를 부록에 둔다"처럼 적는다. 예시는 있지만 규범이 아니어서 그대로 쓰지 않아도 표준 적합이다.
  • 2 — 규범 직렬화 제공. JSON-LD @context(또는 RDF/Turtle 어휘)를 부속서로 수록하고 같은 파일을 별도로 제공한다(운영요령 개정안 제19조의3제2항 병행형). 부속서이므로 표준의 규범 내용이다.

예시 — JSON-LD @context

TTAK.KO-10.0976의 @context 부속서에서 발췌했다. 앞의 요소 정의표 IRI 컬럼이 그대로 기계가 읽는 파일이 된 모습이다.

{
  "@context": {
    "@version": 1.1,
    "dct":  "http://purl.org/dc/terms/",
    "dcat": "http://www.w3.org/ns/dcat#",
    "skos": "http://www.w3.org/2004/02/skos/core#",
    "xsd":  "http://www.w3.org/2001/XMLSchema#",
    "Dataset":  "dcat:Dataset",
    "File":     "dcat:Distribution",
    "Title":    "dct:title",
    "Creator":  { "@id": "dct:creator",  "@type": "@id" },
    "PublicationYear": { "@id": "dct:issued", "@type": "xsd:gYear" },
    "isPartOf": { "@id": "dct:isPartOf", "@type": "@id" },
    "SubjectScheme": { "@id": "skos:inScheme", "@type": "@id" },
    "License":  { "@id": "dct:license",  "@type": "@id" }
  }
}

원본: 부속서_context/TTAK.KO-10.0976_context.jsonld

이 @context 하나만 붙이면, 기존에 {"Title": "…", "PublicationYear": "2016"}처럼 쓰던 JSON 데이터가 그대로 RDF 그래프가 된다. 데이터 쪽을 고칠 필요가 없다는 것이 @context 방식의 장점이다. "@type": "xsd:gYear"는 값의 형식까지 실어 보내므로 ③과도 이어진다.

어느 기술 대상 프로파일이 요구하나

모든 기술 대상 프로파일의 필수다(L1). 자가점검표 4-4의 제출 산출물 목록에서 "JSON-LD @context"가 별표(★) — 모든 표준의 필수 — 로 표시된 것이 이 때문이다.

흔한 함정

  • 부속서에 수록만 하고 파일을 내지 않는 것. 기계가 PDF에서 추출해야 하므로 인정하지 않는다(제19조의3제2항). 반대로 파일만 내고 부속서에 없으면 규범성이 없다.
  • 이용조건을 파일에 적지 않는 것. @context 파일에도 이용조건을 표시해야 한다. JSON은 주석을 쓸 수 없으므로 최상위 $comment 키나 별도 메타 키에 적는다(작성지침 6.6). 이것은 ⑦과 다른 요건이며 별표 10 제4부가 점검한다.
  • ②만 하고 ①을 건너뛰는 것. 요소 이름을 그대로 키로 쓰는 JSON Schema만 내면 형식은 기계가 읽어도 뜻은 모른다. ②는 ①의 매핑을 싣는 그릇이다.

③ 데이터 모델 — 값 형식·제약을 기계가 검증할 수 있나

무엇을 묻는가

데이터에 들어가는 값이 표준을 따르는지를 기계가 자동으로 검사할 수 있는가다. "수온은 0~50℃의 소수", "운용상태는 OFF 또는 READY 중 하나", "수조 식별자는 반드시 하나" 같은 제약을 사람이 읽는 표로만 두면, 데이터 수천 건을 받은 쪽이 적합성을 확인할 방법이 없다.

등급별 모습

  • 0 — 값 유형·제약이 미정의이거나 산문. "센싱값은 실수로 표현한다"처럼 산문으로만 적거나, 데이터 유형 칸이 아예 없다.
  • 1 — 표로 정리, 검증 스키마 미제공. 요소 정의표에 데이터 유형·값 영역·필수 여부·다중성을 표로 정리했다. 사람은 검사할 수 있지만 기계 검증 스키마는 없다. 작성지침 6.5.7의 요소 정의표를 제대로 쓰면 여기까지는 온다.
  • 2 — 기계검증 스키마로 형식화. 같은 제약을 SHACL, XML Schema, JSON Schema 중 하나로 적어 부속서로 낸다. 측정값에는 단위를 QUDT·UCUM 식별자로 결합한다(작성지침 부속서 B.4).

예시 — SHACL 검증 스키마와 단위 결합

TTAK.KO-10.1530의 SHACL 부속서에서 발췌했다. 원 표준의 표 6-1(센서별 측정 범위)과 표 7-x(코드값)가 제약으로 옮겨졌다.

## 수조 — 필수·개수·형식·범위
koai:SectionShape a sh:NodeShape ;
  sh:targetClass koai:WaterTank ;
  sh:property [ sh:path dct:identifier ; sh:name "수조 식별자" ;
                sh:minCount 1 ; sh:maxCount 1 ; sh:datatype xsd:string ] ;
  sh:property [ sh:path koai:fishCount ; sh:name "사육수량" ;
                sh:minCount 1 ; sh:datatype xsd:integer ; sh:minInclusive 0 ] .

## 센서 — 허용 코드값과 단위 IRI
koai:DeviceShape a sh:NodeShape ;
  sh:targetClass sosa:Sensor ;
  sh:property [ sh:path koai:operationStatus ; sh:name "운용상태" ;
                sh:in ( "OFF" "READY" ) ] ;
  sh:property [ sh:path qudt:unit ; sh:name "측정 단위(QUDT IRI)" ;
                sh:minCount 1 ; sh:maxCount 1 ; sh:nodeKind sh:IRI ;
                sh:in ( unit:PH unit:DEG_C unit:L-PER-MIN unit:MilliGM-PER-L unit:NTU ) ] .

원본: 부속서_shacl/TTAK.KO-10.1530_shapes.ttl

단위는 같은 표준의 단위 매핑 부속서가 QUDT IRI와 UCUM 코드를 함께 준다.

koai:unit-pH a skos:Concept ;
  skos:prefLabel "pH"@ko ; rdfs:comment "표 6-1 표기: pH · 측정범위 0~14"@ko ;
  qudt:unit unit:PH ; qudt:ucumCode "[pH]"^^qudt:UCUMcs .

원본: 부속서_units/TTAK.KO-10.1530_units.ttl

이 사례는 2등급이 왜 필요한지도 보여 준다. 원 표준의 단위 코드표에는 본문 단위 목록에 없는 "m/L"이 들어 있었고, 측정값 7.2가 pH인지 용존산소(mg/L)인지 기계가 판단할 근거가 없었다. 단위를 IRI로 결합하고 SHACL로 허용 목록을 정하면 이런 오류가 검증 단계에서 드러난다.

어느 기술 대상 프로파일이 요구하나

기술 대상 프로파일 요구
② 자기기술형 레코드 · 참조표준·물성 필수 — 값과 단위가 내용 자체다
③ AI 데이터세트 필수
① 지식정보 권장
④ 품질 지표 해당 시

흔한 함정

  • 요소 정의표를 2등급으로 착각하는 것. 표가 아무리 자세해도 기계 검증 스키마가 없으면 1등급이다.
  • 단위를 이름 칸에 적는 것. sh:name "수온(℃)"처럼 단위를 자유 텍스트에 넣으면 기계가 검사하지 못한다. 단위는 별도 속성으로 IRI를 적는다.
  • 검증 스키마가 크면 참조형으로. 모듈이 여러 파일로 나뉘거나 문서와 다른 주기로 개정되면 부속서에 규범적 참조 명세만 두고 실물은 외부에 둘 수 있다(제19조의3제3항). 이때 진입점 파일을 반드시 밝힌다.

④ 출처/계보 — 데이터가 어디서 어떻게 왔는지 추적되나

무엇을 묻는가

이 데이터세트를 누가 어떤 활동으로 만들었고, 어떤 원본에서 파생됐는지를 기계가 따라갈 수 있는가다. 사람이 읽는 "제공기관: KISTI, 발행연도 2016" 같은 칸이 있다는 것과, 기계가 "이 파일은 저 데이터세트에서 파생됐고, 저 데이터세트는 이 연구 활동이 생성했다"는 사슬을 따라갈 수 있다는 것은 다르다.

등급별 모습

  • 0 — 출처 정보가 흩어져 있거나 부재. "본 데이터는 ○○사업으로 구축됨" 같은 문장만 있다.
  • 1 — 일부 출처 필드 존재. Publisher, Contributor, PublicationYear 같은 칸이 있다. 누가 냈는지는 알지만 "생성 활동", "파생 관계"를 표현할 수 없고, 다른 표준의 출처 칸과 이름이 달라 기계가 같은 뜻으로 묶지 못한다.
  • 2 — PROV-O로 계보 형식화. W3C PROV-O의 세 뼈대 — Entity(데이터), Activity(만든 활동), Agent(만든 주체) — 로 적고, wasGeneratedBy·wasAttributedTo·wasDerivedFrom로 연결한다.

예시 — PROV-O 계보 그래프

ex:dataset-1436  a prov:Entity, dcat:Dataset ;
  dct:title "Nucleosome positioning on genomic DNA" ;
  dct:identifier <http://dx.doi.org/10.7488/ds/1436> ;
  prov:wasGeneratedBy  ex:observation-study ;   # 어떤 활동이 만들었나
  prov:wasAttributedTo ex:researcher ;          # 누구에게 귀속되나
  prov:wasInfluencedBy ex:funder .              # 연구비 지원 기관

ex:observation-study a prov:Activity ;
  prov:startedAtTime "2015-03-01T00:00:00"^^xsd:dateTime ;
  prov:endedAtTime   "2016-07-19T00:00:00"^^xsd:dateTime ;
  prov:wasAssociatedWith ex:researcher , ex:publisher .

ex:file-1311 a prov:Entity, dcat:Distribution ;
  prov:wasDerivedFrom ex:dataset-1436 .         # 파일 ↔ 데이터세트 파생 관계

원본: 부속서_provo/TTAK.KO-10.0976_prov.ttl

기존 메타데이터 칸이 그대로 PROV 관계로 옮겨진 것을 볼 수 있다. Publisher는 Activity에 참여한 Organization, Contributor(Funder)는 wasInfluencedBy, PublicationYear는 dct:issued다. 요소 정의표에 PROV-O IRI를 매핑해 두면(①) 이 그래프는 자동으로 나온다.

어느 기술 대상 프로파일이 요구하나

기술 대상 프로파일 요구
③ AI 데이터세트 필수 — 학습 데이터는 출처 추적이 핵심이다
① 지식정보 · ② 자기기술형 레코드 권장
④ 품질 지표 적용하지 않음 — 특정 데이터세트를 기술하지 않아 출처가 붙을 곳이 없다

흔한 함정

  • 칸과 그래프의 혼동. 출처 칸이 열 개 있어도 서로 연결되지 않으면 1등급이다. 2등급의 핵심은 Activity를 명시적으로 두는 것이다.
  • 문서 이력과 데이터 계보의 혼동. 표준 문서의 제·개정 이력(작성지침 6.7 f) 표준의 이력)은 데이터의 계보가 아니다.

⑤ 운영 시맨틱 — (ML만) 학습·검증 분할과 역할을 선언했나

무엇을 묻는가

기계학습용 데이터세트에서 어느 레코드가 학습용·검증용·시험용인지, 어느 컬럼이 입력(feature)이고 어느 컬럼이 정답(label)인지를 기계가 읽을 수 있게 선언했는가다. 이 정보가 없어도 데이터 자체는 완전하지만, 학습 파이프라인에 넣으려면 사람이 설명서를 읽고 코드를 짜야 한다.

등급별 모습

  • 0 — ML 대상인데 분할·역할 미선언. 이용자가 파일명(train.csv, test.csv)을 보고 짐작한다.
  • 1 — 일부를 산문으로 기술. "학습 70%, 검증 15%, 시험 15%로 나누며 label 컬럼은 class다"라고 적는다. 사람은 알지만 기계는 못 읽는다.
  • 2 — Croissant로 형식 선언. MLCommons Croissant 1.0으로 RecordSet과 Field를 선언한다. 어떤 파일의 어떤 컬럼이 어떤 데이터 타입이고, 분할은 어느 필드의 어느 값으로 구분되는지를 적는다.

예시 — Croissant 선언

{
  "@type": "sc:Dataset",
  "conformsTo": "http://mlcommons.org/croissant/1.0",
  "dct:conformsTo": "TTAK.KO-10.1594",
  "license": "https://spdx.org/licenses/CC-BY-4.0",
  "distribution": [{
    "@type": "cr:FileObject", "@id": "data.parquet",
    "contentUrl": "https://example.org/ai-model/data.parquet",
    "encodingFormat": "application/x-parquet",
    "sha256": "0000…"
  }],
  "recordSet": [{
    "@type": "cr:RecordSet", "@id": "splits",
    "field": [ { "@id": "splits/name", "dataType": "sc:Text" } ],
    "data": [ { "splits/name": "train" }, { "splits/name": "validation" }, { "splits/name": "test" } ]
  }]
}

원본: 부속서_croissant/TTAK.KO-10.1594_croissant.json

TTAK.KO-10.1594가 정의한 TrainingSet·ValidationSet·TestSet 요소가 Croissant의 splits RecordSet으로 옮겨진 구조다. 이렇게 선언해 두면 Hugging Face나 TFDS 같은 도구가 이 파일만 읽고 데이터를 불러온다.

어느 기술 대상 프로파일이 요구하나

③ AI 데이터세트 프로파일에서만 의미가 있고, 그 안에서도 권장(L3)이다. 다른 기술 대상 프로파일에서는 "해당 없음(N·A)"으로 적는다. 자가점검표 4-4의 "Croissant ML 계층"이 "③ AI 데이터세트(학습 분할)만"으로 한정된 이유다.

흔한 함정

  • 비율만 적는 것. 분할 비율은 1등급이다. 2등급은 어느 레코드가 어느 분할에 속하는지를 기계가 결정할 수 있어야 한다.
  • 기준선 없이 얹는 것. Croissant는 schema.org Dataset 위에 올라가므로 ①②가 먼저 되어 있어야 한다. 별표 10이 "⑤는 ③에 의존한다"고 적은 이유다.

⑥ 품질 측도 — 품질을 형식 어휘로 붙였나

무엇을 묻는가

데이터가 얼마나 정확하고 완전하며 균형 잡혀 있는지를, 국제 품질 측도에 연결된 측정값으로 기계가 읽을 수 있게 붙였는가다. "측도"는 ISO/IEC 5259-2(데이터 품질 측도)가 정한 품질 측정 방법(measure)을 뜻하며, ISO/IEC 25012(데이터 품질 모델)의 품질 차원에 속한다. 이 구성요소는 수준 요건 명세서 v0.3에서 "품질 프로파일"이라 불렀으나, 제2부의 기술 대상 프로파일과 구분하기 위해 "품질 측도"로 바꿔 부른다.

등급별 모습

  • 0 — 품질 신호가 enum 코드뿐. "A등급/B등급" 같은 자체 코드만 있어, 무엇을 재서 나온 값인지 기계가 모른다.
  • 1 — 일부 품질 표기. 정확도·결측률 같은 수치를 적지만 표준마다 이름이 제각각이고, 어느 국제 품질 차원인지 연결이 없다.
  • 2 — 국제 측도에 연결해 DQV·SHACL로 표현. W3C DQV로 측정값(QualityMeasurement)을 적고, 각 측정값이 ISO/IEC 5259-2의 어느 측도인지(isMeasurementOf) 가리킨다. 합격 기준은 SHACL 제약으로 적어 자동 검증에 쓴다.

예시 — DQV 품질 측정값

ex:autonomous-dataset a dcat:Dataset ;
  dct:conformsTo "TTAK.KO-11.0310" ;
  dqv:hasQualityMeasurement ex:m-accuracy, ex:m-sufficiency, ex:m-balance, ex:m-diversity .

ex:m-accuracy a dqv:QualityMeasurement ;
  dqv:isMeasurementOf iso5259:syntacticAccuracyRate ;   # 어느 품질 측도인가
  dqv:computedOn ex:autonomous-dataset ;
  dqv:value "0.950"^^xsd:double ;
  dct:description "제공 10,000건 중 오류 500건 → 0.95 (품질목표 0.99 미달)" .

ex:m-balance a dqv:QualityMeasurement ;
  dqv:isMeasurementOf iso5259:classBalanceIndex ;
  dqv:value "0.86"^^xsd:double ;
  dct:description "위반유형 7종 분포 10~17.5% → 균형 지수 0.86" .

원본: 부속서_quality/TTAK.KO-11.0310_quality.ttl

0310 표준 본문의 "구문 정확성 99% 이상", "분류체계별 수량 균일성" 같은 요구가 각각 syntacticAccuracyRate, classBalanceIndex라는 국제 측도에 정렬됐다. "이 데이터세트는 품질 목표를 충족하는가"를 SHACL 한 줄(값 ≥ 0.99)로 자동 판정할 수 있다.

어느 기술 대상 프로파일이 요구하나

기술 대상 프로파일 요구
④ 품질 지표 권장 — 사실상 핵심 산출물
③ AI 데이터세트 권장(L3)
② 중 참조표준·물성 권장 — 불확도가 데이터의 값어치를 좌우한다

흔한 함정

  • 요구사항과 측정값의 혼동. 표준은 "99% 이상이어야 한다"는 요구를 정하고, 데이터세트는 "0.95다"라는 측정값을 붙인다. 2등급은 측정값이 어느 측도의 값인지 IRI로 밝힌 상태다.
  • 자체 지표 이름. "정확도"라는 이름만으로는 ISO/IEC 5259-2의 여러 정확성 측도 중 무엇인지 알 수 없다.

⑦ 접근/사용 제약 — 누가 어떻게 써도 되는지 기계가 판단하나

무엇을 묻는가

이 데이터를 누가, 어떤 목적으로, 어떤 조건에서 쓸 수 있는지를 기계가 읽고 판단할 수 있는가다.

별표 10 제4부와 혼동하지 않는다. ⑦은 그 표준을 따라 쌓인 데이터의 이용조건이다. 제4부는 표준이 제공하는 기계가독 산출물(스키마 파일) 자체의 이용조건이다. 둘은 별개이며 각각 충족해야 한다.

등급별 모습

  • 0 — 라이선스·접근권 메타데이터 부재. 데이터를 받은 사람이 써도 되는지 알 수 없다.
  • 1 — 문서 수준 저작권만. 표준 문서 표지의 "본 표준의 저작권은 TTA에 있다"는 문서의 저작권이지 데이터의 이용조건이 아니다. 데이터 메타데이터에 "라이선스: 공공누리 1유형"이라고 글자로만 적은 것도 1등급이다.
  • 2 — 데이터 수준에서 명시. dct:license에 SPDX 식별자 같은 IRI를 적고, 단순 라이선스로 표현되지 않는 조건(비상업적 이용만, 특정 기관만 접근 등)은 ODRL 정책으로, 연구 목적 제한은 DUO(Data Use Ontology) 코드로 적는다.

예시 — ODRL 이용정책

{
  "@type": "Offer",
  "uid": "https://std.tta.or.kr/policy/1594/model-offer",
  "permission": [{
    "target": "https://example.org/ai/model/kobert-sentiment",
    "action": [ "use", "reproduce", "distribute", "modify" ],
    "duty": [{ "action": "attribute",
      "constraint": [{ "leftOperand": "source", "operator": "eq",
                       "rightOperand": "https://spdx.org/licenses/Apache-2.0" }] }]
  }],
  "prohibition": [{
    "target": "https://example.org/ai/model/kobert-sentiment",
    "action": [ "aggregate" ],
    "constraint": [{ "leftOperand": "purpose", "operator": "eq",
                     "rightOperand": { "@id": "duo:DUO_0000046" } }]
  }]
}

원본: 부속서_odrl/TTAK.KO-10.1594_policy.jsonld — DUO_0000046은 "비상업적 이용만"

허용 행위(permission), 그에 따르는 의무(출처 표시 duty), 비상업적 이용으로 한정하는 금지(prohibition)가 기계가 읽는 규칙으로 적혀 있다. 데이터 카탈로그나 접근 통제 시스템이 이 정책을 읽어 "이 요청자가 이 목적으로 받아가도 되는가"를 자동 판단한다.

어느 기술 대상 프로파일이 요구하나

기술 대상 프로파일 요구
① 지식정보 권장 — "누가 어떤 조건으로 쓸 수 있나"가 카탈로그의 핵심 기능이다
③ AI 데이터세트 권장(L3)

별표 10은 ⑦이 "아무것에도 의존하지 않는다"고 적는다. 시맨틱·구조와 무관하게 이용조건만 먼저 형식화할 수 있다는 뜻이다.

흔한 함정

  • 문서 저작권 문구를 데이터 이용조건으로 착각하는 것. 가장 흔하다.
  • 글자로 적는 것. "라이선스: CC BY 4.0"은 1등급이고, https://spdx.org/licenses/CC-BY-4.0 같은 IRI로 적어야 2등급이다.

일곱 구성요소를 한 장으로

구성요소 기계가 답할 수 있게 되는 질문 구현 어휘 묶음 필수인 기술 대상 프로파일
① 시맨틱 이 요소는 무슨 뜻인가 SKOS · DCMI Terms · DCAT · schema.org L1 전부
② 신태틱 그 뜻을 파일로 받아 해석할 수 있나 JSON-LD 1.1 · RDF/Turtle L1 전부
③ 데이터 모델 값이 맞는지 자동으로 검사할 수 있나 SHACL · XSD · JSON Schema · QUDT · UCUM L2 ② 자기기술형 · ③ AI 데이터세트
④ 출처/계보 어디서 어떤 활동으로 만들어졌나 PROV-O · DCMI Terms L2 ③ AI 데이터세트
⑤ 운영 시맨틱 어느 레코드가 학습·검증·시험용인가 Croissant 1.0 L3 — (③에서 권장)
⑥ 품질 측도 얼마나 좋은지, 그 수치는 어느 국제 측도인가 DQV · SHACL · ISO/IEC 5259-2·25012 L3 — (④·③·참조표준에서 권장)
⑦ 접근/사용 제약 누가 어떤 목적으로 써도 되나 dct:license(SPDX) · ODRL · DUO L3 — (①·③에서 권장)

의존 관계. L1(①②)은 모든 구성요소의 기준선이다. ⑤·⑥은 ③에 의존하고 ④에는 의존하지 않으며, ⑦은 아무것에도 의존하지 않는다. 그래서 별표 10은 요구 수준을 L1→L2→L3의 계단이 아니라 기술 대상 프로파일별 구성요소로 정한다.

판정과 기재. 제안자는 별지 제11-1호서식 1절에 기술 대상 프로파일과 목표 수준(필수만/권장까지)을 적는다. 에디터는 표준초안을 완성한 뒤 별지 제21-1호서식 1부에 구성요소별 현재 등급과 증빙 위치를 적고, 기술위원회등 의장이 확인해 표준안과 함께 제출한다(운영요령 개정안 제21조제5항). 기술 대상 프로파일의 필수 구성요소가 모두 2등급이면 AI-Ready 수준을 충족한다(별표 10 제5부).
