# 스키마 형식과 제공 방법 분석

**구성** — 1부 스키마 형식 분석 · **1부-보론 사례별 배경(만든 곳·목적·연혁·최신 버전)** · 2부 제공 방법 분석 · 3부 TTA 적용 권고

## 가장 중요한 발견

**조사한 16개 사례 중, 스키마를 표준 문서 파일 안에 담은 사례는 0건이다.**

PDF 3종(ECMA-424 2판, NIST AI 100-1, PREMIS Data Dictionary)을 압축 스트림까지 풀어 검사한 결과, 스키마 본문도 PDF 첨부파일(EmbeddedFile)도 없었다. ECMA-424는 CycloneDX 스키마를 Ecma가 정식 승인한 표준인데도 566쪽 본문에 스키마 코드가 한 줄도 없고, GitHub 저장소를 규범적으로 참조할 뿐이다.

즉 국제 관행은 **"문서에 담는다"가 아니라 "문서가 외부 스키마를 규범적으로 참조한다"** 이다. 표준 문서와 스키마는 물리적으로 분리하되, 문서에서 스키마의 위치·버전·규범성을 명시하는 방식이다.

## 1-2. 형식 선택의 세 가지 패턴

### 패턴 A — 단일 형식(XSD 전용): 도서관·지리·사회과학 계열

ISO 19115-3, PREMIS, MODS, METS, GML, DDI가 모두 XSD 하나만 낸다. 공통점은 **2000년대에 확립된 XML 기반 표준**이고, 구현체가 이미 XML 처리계에 고정돼 있다는 점이다. 새 형식을 추가할 유인이 없다.

한계는 분명하다. JSON·RDF 생태계에서 이 표준을 쓰려면 이용자가 스스로 변환해야 하고, 변환의 정확성은 아무도 보증하지 않는다.

### 패턴 B — 다중 형식 병행: SBOM·의료 계열

CycloneDX(XSD·JSON Schema·Protobuf), FHIR(XSD·JSON Schema·ShEx·GraphQL·Turtle)가 대표적이다. **구현 생태계가 여러 기술 스택에 걸쳐 있을 때** 선택하는 방식이다.

CycloneDX는 3종을 **동등한 규범**으로 두고, FHIR은 StructureDefinition을 규범으로 두고 나머지를 생성물로 둔다. 전자는 형식 간 불일치 위험을 감수하는 대신 각 형식이 자연스럽고, 후자는 일관성이 보장되는 대신 생성기가 곧 병목이 된다.

### 패턴 C — 단일 원천 + 자동 생성: 기계가독 우선 설계

OSCAL의 Metaschema, SPDX의 SHACL 모델, Schema.org의 `schema.ttl`이 각각 단일 원천이고, 배포되는 XSD·JSON Schema·각종 직렬화는 **모두 그로부터 생성**된다.

이 패턴이 갖는 결정적 장점은 **형식 간 불일치가 원천적으로 발생하지 않는다**는 것이다. TTA가 AI-Ready 표준을 설계한다면 이 패턴이 목표점이 되어야 한다. 다만 생성 파이프라인 구축·유지 비용이 크다.

## 1-3. 형식별 실무 특성

| 형식 | 검증 도구 | 라이선스 주석 | 사람 가독성 | 주 용도 |
|---|---|---|---|---|
| **XSD** | 성숙(모든 언어) | XML 주석 가능 | 낮음 | XML 문서 검증, 레거시 연계 |
| **JSON Schema** | 성숙 | **주석 불가** → `$comment` 우회 | 중간 | 웹 API, 최근 표준의 기본값 |
| **Turtle/RDF** | SHACL·ShEx 필요 | `#` 주석 + `dcterms:license` 트리플 | 중간 | 어휘·온톨로지, 링크드 데이터 |
| **JSON-LD 컨텍스트** | 별도 검증기 필요 | 주석 불가 | 낮음 | JSON을 RDF로 해석 |
| **SHACL/OWL** | 전용 엔진 | `#` 주석 | 낮음 | 제약 규칙의 형식적 표현 |
| **Protobuf** | 성숙 | `//` 주석 가능 | 높음 | 고성능 직렬화 |
| **ShEx/GraphQL** | 제한적 | `#` 주석 | 중간 | 특수 목적 |

**메타데이터 표준에 한정하면 Turtle과 JSON Schema가 사실상의 표준 조합**이다. DCAT·DCMI·Croissant·Schema.org가 모두 RDF 계열을 채택했고, 최근 만들어진 SPDX 3.0은 SHACL(규범) + JSON Schema(생성물) 조합을 쓴다.

# 1부-보론. 사례별 배경

각 표준이 **누가·왜·언제** 만들어졌고 지금 어디까지 왔는지 정리한다. 버전과 날짜 중 ★ 표시는 이 폴더에 수집한 **실물 파일에서 직접 확인**한 값이고, 나머지는 공개된 연혁이다.

## 유형 1. 기계가독 우선 설계

### NIST OSCAL — Open Security Controls Assessment Language

| | |
|---|---|
| 만든 곳 | 미국 국립표준기술연구소(NIST) 정보기술연구소 |
| 시작 | 2017년경 |
| 최신 | **v1.2.3** ★ (릴리스 자산 52종) |
| 목적 | 보안 통제(security control)의 카탈로그·프로파일·시스템보안계획·평가결과를 **기계가 처리할 수 있는 언어로 표현** |

미국 연방기관은 FedRAMP·FISMA 등에 따라 수백 쪽짜리 보안 통제 문서를 주고받는데, 이를 사람이 읽고 표에 옮기는 작업이 병목이었다. OSCAL은 그 문서 자체를 기계가독 형식으로 바꿔 **컴플라이언스 검증을 자동화**하려는 시도다. 이른바 *compliance as code*의 대표 사례.

설계가 특징적이다. XSD도 JSON Schema도 손으로 쓰지 않고, **Metaschema라는 자체 모델링 언어**로 모델을 한 번만 정의한 뒤 XSD·JSON Schema·XML↔JSON 변환기(XSLT)를 자동 생성한다. 수집본 기준 원천 metaschema 14개에서 산출물 36개가 나온다.

### HL7 FHIR — Fast Healthcare Interoperability Resources

| | |
|---|---|
| 만든 곳 | HL7 International (보건의료 정보 표준화 단체) |
| 시작 | 2011~2012년 초안, 2014년 첫 DSTU |
| 최신 | **R5 = v5.0.0** ★ (XSD 생성 시각 2023-03-26 ★) |
| 목적 | 의료 데이터를 **REST API로 주고받을 수 있는 리소스 단위**로 재설계 |

앞선 HL7 v2(메시지)·v3(RIM)이 너무 복잡해 구현이 어렵다는 반성에서 나왔다. 진료기록·환자·처방 등을 "리소스"로 쪼개고 웹 표준(REST·JSON)에 얹은 것이 핵심이다.

수집본에서 확인되는 규모가 이 표준의 성격을 말해 준다 — **XSD 323개**, JSON Schema, ShEx, GraphQL, RDF/Turtle이 한 빌드에서 함께 나온다. 원천은 StructureDefinition이라는 리소스 정의이고 나머지는 전부 생성물이다.

### SPDX — System Package Data Exchange

| | |
|---|---|
| 만든 곳 | Linux Foundation SPDX 워킹그룹 |
| 시작 | 2010년 |
| 최신 | **v3.0.1** ★ |
| 표준화 | **ISO/IEC 5962** (2021년 국제표준 채택) |
| 목적 | 소프트웨어 구성요소·라이선스·출처를 기술하는 **SBOM(Software Bill of Materials)** 형식 |

오픈소스를 조합해 제품을 만들 때 "이 안에 무엇이 들어 있고 각각 라이선스가 무엇인가"를 주고받을 공통 형식이 필요해 시작됐다. 2021년 로그4j 사태 이후 각국이 SBOM을 요구하면서 급격히 중요해졌다.

3.0에서 **SHACL 모델을 원천**으로 삼고 JSON Schema를 생성하는 구조로 바뀌었다. 저장소에 `docs/`(산문)·`ontology/`(모델)·`schemas/`(생성물)가 나란히 있다.

### CycloneDX

| | |
|---|---|
| 만든 곳 | OWASP → **Ecma International TC54**로 이관 |
| 시작 | 2017년 |
| 최신 | 스키마 **bom-1.7** ★ · **ECMA-424 제2판(2025-12)** ★ |
| 목적 | SBOM 형식. SPDX와 경쟁·병존 관계 |

SPDX가 라이선스 컴플라이언스에서 출발했다면 CycloneDX는 **보안 취약점 추적**에서 출발했다. 그래서 구성요소 식별·의존성 그래프·취약점 정보에 강하다.

이 사례가 특별한 이유는 **거버넌스 이중화**다. 스키마는 GitHub에서 개발·배포하되 같은 버전을 Ecma가 국제표준(ECMA-424)으로 승인한다. 방법1의 "협회 보관본이 정본" 구조가 여기서 왔다.

## 유형 2. 공용 구조화 DB

### NIST AI RMF 1.0 / CPRT

| | |
|---|---|
| 만든 곳 | NIST (AI RMF 본문) · NIST 응용사이버보안부(CPRT 플랫폼) |
| 발간 | AI RMF 1.0 — **2023년 1월** (NIST AI 100-1) |
| CPRT 등재 | **2026-02-19** |
| 최신 | 프레임워크 버전 식별자 `AI_100_1_0_0` ★ |
| 목적 | AI 위험 관리 프레임워크. GOVERN·MAP·MEASURE·MANAGE 4개 기능 |

AI RMF 자체는 **산문 프레임워크**다. 기술 표준이 아니라 조직이 AI 위험을 다루는 방법을 서술한 문서로, 자발적(voluntary) 성격이다.

주목할 것은 **CPRT(Cybersecurity and Privacy Reference Tool)** 쪽이다. NIST는 CSF·Privacy Framework·SP 800-53 등 서로 다른 문서 표준의 구조화 콘텐츠를 **하나의 공용 스키마**(`documents`·`elements`·`relationship_types`·`relationships`)에 담아 REST API로 제공한다. 수집본 기준 **209개 프레임워크 버전**이 등재돼 있고, AI RMF(요소 1,960/관계 1,956)와 CSF 2.0(906/1,566)이 같은 구조를 쓰는 것을 실증했다. ★

## 유형 3. 네임스페이스 URI 역참조

### W3C DCAT 3 — Data Catalog Vocabulary

| | |
|---|---|
| 만든 곳 | W3C Dataset Exchange 워킹그룹 |
| 연혁 | DCAT 1 (2014) → DCAT 2 (2020) → **DCAT 3 권고안 2024-08-22** ★ |
| 목적 | 데이터 카탈로그를 웹에서 상호운용 가능하게 기술하는 어휘 |

정부·기관마다 다른 데이터 포털의 목록을 한데 모아 검색할 수 있게 하려는 목적에서 출발했다. EU의 DCAT-AP, 한국 공공데이터포털 등 각국 프로파일의 기반이다. AI-Ready 메타데이터 표준을 만들 때 **가장 먼저 인용하게 되는 어휘**다.

어휘 파일 `dcat.ttl` 안에 `dcterms:license` 트리플로 자기 라이선스(CC BY 4.0)를 선언하는 점이 특징. ★

### W3C PROV-O — Provenance Ontology

| | |
|---|---|
| 만든 곳 | W3C Provenance 워킹그룹 |
| 최신 | **권고안 2013-04-30** ★ (이후 개정 없음) |
| 목적 | 데이터가 **누가·무엇으로·어떻게** 만들어졌는지를 기술하는 온톨로지 |

Entity(대상)·Activity(행위)·Agent(주체) 세 축으로 이력을 표현한다. 2013년에 확정된 뒤 바뀌지 않았는데, 이는 정체가 아니라 **모델이 충분히 일반적이어서 개정이 불필요**했다고 보는 편이 맞다. EU AI Act가 고위험 AI의 학습데이터 출처 추적을 요구하면서 다시 주목받고 있다.

### DCMI — Dublin Core Metadata Terms

| | |
|---|---|
| 만든 곳 | Dublin Core Metadata Initiative |
| 시작 | **1995년** (오하이오주 더블린 워크숍에서 유래한 이름) |
| 최신 | DCMI Metadata Terms **2020-01-20** ★ |
| 목적 | 모든 자원에 공통으로 쓸 수 있는 **최소 메타데이터 15개 요소**에서 출발 |

`title`·`creator`·`subject`·`date` 같은 기본 요소를 정의한다. 메타데이터 어휘의 **조상 격**이며, DCAT·schema.org를 비롯한 후대 어휘가 모두 이를 참조하거나 흡수했다. ISO 15836으로도 표준화됐다.

30년 된 어휘가 여전히 현역인 이유는 **범위를 좁게 유지**했기 때문이다. 도메인 특수성을 욕심내지 않고 공통분모만 정의했다.

| 최신 | 저장소에 **spec 1.0과 1.1** 병존 ★ + RAI·Geo 확장 |

기존 메타데이터 어휘로는 "이 데이터세트의 어느 부분이 학습용이고 어느 필드가 레이블인가"를 기계가 알 수 없었다. Croissant는 schema.org를 확장해 이를 데이터세트 수준에서 한 번 선언하게 한다. Hugging Face·Kaggle·OpenML이 지원한다.

가장 최근 사례이고, AI-Ready 논의와 **문제의식이 가장 가깝다.**

## 유형 5. 문서 유료 + 스키마 무료

### ISO 19115-3

| | |
|---|---|
| 만든 곳 | **ISO/TC 211** (지리정보/지오매틱스 기술위원회) |
| 계보 | ISO 19115(개념 모델) → 19139(XML 구현) → **19115-3(현행 XML 구현)** |
| 최신 | 수집본 기준 mdb 모듈 **2.0** ★ (ISO 카탈로그 번호 80874) |
| 목적 | 지리정보 메타데이터를 XML로 표현하는 **구현 명세** |

국가공간정보포털·국토지리정보원 등 국내 공간정보 체계가 이 계열을 따른다. **개념 모델(19115-1)과 XML 구현(19115-3)을 분리**한 구조가 특징이다.

병행 배포 관점에서 중요한 사례다. 문서 본문은 iso.org에서 **유료 판매**하지만 규범 XSD는 standards.iso.org에 **무료 공개**한다(수집본 XSD 117개). 유료 문서 체계 안에서도 스키마 개방이 성립함을 보여준다. 다만 XSD 어디에도 라이선스 표기가 없어 재배포 가능 여부를 알 수 없다는 문제가 있다. ★

## 2-1. 여덟 가지 제공 방법

| # | 제공 방법 | 사례 | 접근 URL 형태 |
|---|---|---|---|
| 1 | **표준 문서 내 포함** | **없음** | — |

| 3 | 전용 스키마 저장소 사이트 | OGC, ISO 19115-3 | `schemas.opengis.net`, `standards.iso.org` |
| 4 | 네임스페이스 URI 역참조 | W3C DCAT·PROV-O, DCMI | `www.w3.org/ns/dcat` (콘텐츠 협상) |
| 5 | GitHub 릴리스 자산 | OSCAL, CycloneDX | `github.com/.../releases/download/v1.2.3/...` |

## 2-2. 방법별 상세

### ② 같은 웹 디렉터리 병행 게시 — 가장 단순하고 즉시 적용 가능

LoC PREMIS는 `/standards/premis/v3/` 아래에 `premis-3-0-final.pdf`(문서)와 `premis.xsd`(스키마)를 나란히 둔다. 이용자가 문서를 찾으면 스키마도 자동으로 눈에 들어온다.

**장점**: 추가 인프라가 필요 없다. 기존 표준 게시 체계에 파일을 하나 더 올리면 끝이다.
**단점**: 버전 관리·이력 추적 기능이 없다. 변경 이력은 파일명(`mods-3-8.xsd`)에만 남는다.

### ③ 전용 스키마 저장소 사이트 — 다수 표준을 한 곳에

OGC는 `schemas.opengis.net`에 모든 표준의 XSD를 모으고, 표준별 디렉터리 + **전체 일괄 zip**(`SCHEMAS_OPENGIS_NET.zip`, 42.6MB)을 제공한다. ISO도 `standards.iso.org`에 두고 **모듈별 zip**(`mdb.zip`, 32KB)과 **전체 zip**(`19115AllNamespaces.zip`, 10.4MB)을 함께 낸다.

**핵심 설계**: 개별 파일 접근(schemaLocation이 가리키는 실제 URL)과 일괄 다운로드를 **모두** 제공한다. 전자는 런타임 검증용, 후자는 오프라인 개발용이다. 둘 중 하나만 있으면 반쪽이다.

**단점**: 표준 문서와 물리적으로 분리돼, 문서만 본 이용자는 스키마의 존재를 모를 수 있다. ISO가 이 문제를 그대로 안고 있다.

### ④ 네임스페이스 URI 역참조 — 메타데이터 표준의 정석

같은 URI에 `Accept` 헤더만 바꿔 요청했을 때의 실제 응답을 확인했다.

| 요청 `Accept` | `https://www.w3.org/ns/dcat` 응답 |
|---|---|
| `text/turtle` | `text/turtle; charset=utf-8` |
| `application/rdf+xml` | `application/rdf+xml` |
| `application/ld+json` | `application/ld+json` |
| `text/html` | `text/html; charset=utf-8` |

**하나의 URI가 사람에게는 HTML 문서를, 기계에게는 요청한 형식의 어휘 파일을 준다.** DCMI(`purl.org/dc/terms/`)도 동일하게 작동한다.

이것이 중요한 이유는, 스키마 안에서 다른 스키마를 참조할 때 **참조 URI가 곧 다운로드 URI가 되기 때문**이다. AI 에이전트가 데이터에서 네임스페이스 URI를 발견하면 그 자리에서 정의를 가져올 수 있다. AI-Ready 관점에서 가장 진보한 방식이다.

**단점**: 서버 설정(콘텐츠 협상)이 필요하고, 네임스페이스 URI를 영구히 유지해야 한다(URI 영속성 정책).

### ⑤ GitHub 릴리스 자산 — 버전 고정과 무결성

OSCAL은 릴리스마다 자산 52종을 태그(`v1.2.3`)에 묶어 올린다. 릴리스 URL은 불변이고, GitHub API로 자산 목록·크기·해시를 기계적으로 조회할 수 있다.

**장점**: 버전이 태그로 고정돼 "어느 버전의 스키마인가"가 절대 모호하지 않다. 릴리스 노트가 변경 이력이 된다.
**단점**: 특정 상용 플랫폼(GitHub)에 종속된다. 표준화 기구의 영속성 요구와 상충할 수 있다.

CycloneDX가 이 문제를 푸는 방식이 참고할 만하다. **스키마는 GitHub에서 배포하되, 같은 버전을 Ecma가 ECMA-424 정식 판으로 승인**해 공식성과 영속성을 확보한다. 이중 트랙 구조다.

### ⑥ GitHub 저장소 자체 — 문서와 스키마의 동거

Schema.org·Croissant·SPDX는 저장소 자체가 배포 경로다. SPDX 저장소에는 `docs/`(스펙 산문), `ontology/`(SHACL·OWL), `schemas/`(JSON Schema)가 나란히 있고, Croissant는 `docs/`에 `croissant-spec-1.0.md`와 `croissant.ttl`이 같은 디렉터리에 있다.

**장점**: 문서와 스키마가 **하나의 커밋으로 함께 변경**된다. 불일치가 구조적으로 방지된다.
**단점**: 이용자가 저장소 구조를 알아야 한다. 어느 파일이 규범인지 별도 안내가 필요하다.

### ⑦ 전용 다운로드 페이지(zip 번들) — 대규모 표준

FHIR은 `downloads.html` 한 페이지에 zip·tgz 19종을 정리한다. 정의(JSON·XML), 스키마(XSD·JSON Schema·ShEx·GraphQL), 예제, 패키지(npm식 `.tgz`)가 목적별로 나뉜다.

**장점**: 이용자가 자기 용도에 맞는 번들만 받는다. 전체 XSD 323개를 개별 다운로드할 필요가 없다.
**단점**: 페이지 유지 비용. 파일명 규칙이 흔들리면 링크가 깨진다(실제로 원본 PDF가 기재한 `definitions.shex.zip`은 404였고 실제 이름은 `fhir.schema.shex.zip`이었다).

### ⑧ 구조화 DB + REST API — 다수 표준의 통합 질의

NIST CPRT는 209개 프레임워크 버전을 **단일 스키마의 DB**에 담고 REST API로 낸다.

```
/framework/version/{버전ID}/export/{json|excel}?element=all
/framework/version/{버전ID}/element/all/graph
```

**장점**: 서로 다른 표준을 **교차 질의**할 수 있다. AI RMF와 CSF 2.0의 통제항목을 같은 코드로 처리할 수 있는 이유다. 관계(relationships) 정보까지 기계가독으로 제공된다.
**단점**: 구축·운영 비용이 가장 크다. API 문서화가 부실하면 접근이 어렵다(CPRT 자체가 그렇다 — 카탈로그 페이지가 JS 기반이라 API 엔드포인트를 프론트엔드 번들에서 역추적해야 했다).

## 2-3. 제공 방법의 조합

성숙한 표준일수록 **한 가지 방법만 쓰지 않는다.**

| 사례 | 조합 |
|---|---|
| CycloneDX | GitHub 저장소 + GitHub 릴리스 + Ecma 정식 발간 + `cyclonedx.org` 스키마 URL |
| ISO 19115-3 | 전용 저장소 사이트 + 모듈별 zip + 전체 zip + (원천은 GitHub `ISO-TC211/XML`) |
| Schema.org | GitHub 저장소 + `schema.org/version/latest/` 릴리스 URL + 네임스페이스 역참조 |
| W3C DCAT | 권고안 페이지 + 네임스페이스 역참조 |

**최소 조합은 ②(문서 옆 게시) + ⑤ 또는 ⑥(버전 관리)** 이다. 전자는 발견성을, 후자는 이력 추적을 담당한다.

# 3부. TTA 적용 권고

## 3-1. 형식

**필수 2종 + 선택 1종**을 권고한다.

| 구분 | 형식 | 근거 |
|---|---|---|
| **필수** | JSON Schema | 최근 표준의 기본값. 웹 API·AI 파이프라인 연계 |
| **필수** | Turtle(RDF) | 메타데이터 표준의 정석. 네임스페이스 역참조·링크드 데이터 |
| **선택** | XSD | 기존 XML 기반 국내 시스템 연계가 필요한 경우에만 |

**단일 원천 + 자동 생성(패턴 C)을 목표로 하되, 초기에는 형식별 수기 작성을 허용**하고 형식 간 일치를 검증하는 절차를 두는 것이 현실적이다. 처음부터 생성 파이프라인을 요구하면 표준 제안 자체가 위축된다.

## 3-2. 제공 방법

**표준 문서에 스키마를 첨부하는 방식은 국제 관행에 없다.** 대신 다음 3단 구조를 권고한다.

1. **표준 문서**에 스키마의 **규범적 참조**를 명시한다 — URL, 버전, 해시, 그리고 "이 스키마가 규범인지 참고인지"를 본문에 적는다. ECMA-424가 쓰는 방식이다.
2. **TTA 표준 다운로드 페이지의 표준 문서 옆에** 스키마 파일을 함께 게시한다(방법 ②). 발견성을 확보하는 최소 조치이며, 기존 인프라로 즉시 가능하다.
3. **버전 관리는 GitHub 릴리스**(방법 ⑤)로 한다. 태그로 버전을 고정하고, 릴리스 노트를 변경 이력으로 삼는다.

**중장기 과제**로 네임스페이스 URI 역참조(방법 ④)를 검토한다. `standard.tta.or.kr/ns/...` 같은 영속 URI 체계를 세우고 콘텐츠 협상을 설정하는 일인데, 서버 설정 자체는 어렵지 않으나 **URI 영속성 정책**(표준 폐지 후에도 URI를 유지한다는 약속)이 규정에 먼저 들어가야 한다.

## 3-3. 작성지침에 넣어야 할 항목

수집 과정에서 실제로 문제가 됐던 것들이다.

1. **규범성 표시** — 여러 형식을 낼 때 어느 것이 규범이고 어느 것이 생성물인지 명시. OSCAL·SPDX·Schema.org는 명확하고, CycloneDX는 3종 동등이라 별도 명시가 필요하다.
2. **진입점 표시** — OGC `gml.xsd`와 ISO `mdb.xsd`는 다른 모듈을 include/import하는 진입점일 뿐이라, 그 파일만 받으면 동작하지 않는다. 수집 중 실제로 겪은 문제다. 진입점 여부와 의존 모듈 목록을 명시해야 한다.
3. **일괄 다운로드 제공** — 모듈이 여럿이면 개별 URL과 함께 zip을 제공한다. ISO·OGC가 모두 그렇게 한다.
4. **파일명 규칙 고정** — FHIR의 `definitions.shex.zip` → `fhir.schema.shex.zip` 사례처럼 파일명이 바뀌면 문서의 링크가 깨진다. 버전을 파일명에 넣는 규칙(`mods-3-8.xsd`)을 정해두는 것이 안전하다.
5. **라이선스 파일 내 표기** — 형식별 표기 방법은 [저작권-라이선스-분석.md](저작권-라이선스-분석.md) 참조.
